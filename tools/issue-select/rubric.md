# Rubric: is this a good first issue?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Repo not archived | The repo-facts `archived:` flag (eval) / the "This repository has been archived" banner on the repo front page (live) | Passes when `archived: no` / no banner is shown. | required |
| Repo push-recent | The `last push to any branch` date in repo-facts (eval) / the newest commit date on the repo front page (live), measured against the bundle's `captured:` date (eval) or today (live) | Passes when the last push is within 180 days of the measurement date. | required |
| Human maintainer activity | The `maintainer first-response sample` list (days to first owner/member/collaborator reply, across 5 recently-updated issues) AND the `last 5 default-branch commits` list with each commit's author (eval) / the same two signals gathered live per `references/evidence-guide.md` | Passes when EITHER: (a) at least one issue in the first-response sample got an owner/member/collaborator reply within 90 days of that issue being opened, OR (b) at least 1 of the last 5 default-branch commits is authored by a human account (username does not end in `[bot]`, and is not a bot merging its own scheduled job with no human co-author) dated within 30 days of the measurement date. A lone human maintainer with no other committers or issue replies yet (e.g. a freshly-opened repo) still passes on (b) alone — the bar is "a human is demonstrably behind this," not a headcount. Fails only when neither signal is present (e.g. a stale response sample AND commits that are old and/or bot-only). | required |
| Bounded scope | The issue body and comment thread, plus the issue's age (opened date) and its linked-PR history (eval bundle text / issue body + thread + Development box live) | Fails ONLY when any of: the issue explicitly describes itself as an umbrella/tracking issue or "megaissue" meant to be split across separate issues or PRs by different people; the ask spans an open-ended, never-finished slice of the codebase with no fixed, nameable boundary ("add more X wherever it makes sense," "anywhere in the codebase") rather than a specific, enumerable set of items; the thread shows a genuinely unresolved design debate with no maintainer decision, especially alongside prior abandoned (closed, unmerged) PRs attempting it; a maintainer states outright that the fix touches core internals; or the issue has been open more than 2 years AND has 2 or more closed/unmerged linked PRs in its history (repeated abandoned attempts are themselves evidence the real fix is harder than the surface description suggests, even if the original description and any early maintainer reply read as settled). A terse one-liner, a checklist of several concrete sub-steps that all serve one coherent change (e.g. add a new docs page plus update the handful of existing pages that currently point to the old guidance), or a short list of specific named items to add/fix, all still PASS — grade the boundedness of the actual requested change, not its word count, file count, or item count. A pure usage/support question ("how do I get this to work?") always fails this check. | required |
| Unclaimed | The `this issue: assignees` / `linked PRs` line (eval) / the Assignees box + Development box + comment thread (live) | Fails when any of: the assignees field is non-empty; any linked PR is in the `open` state; or the most recent activity in the thread is an unanswered claim comment ("I'll take this" / "working on this") less than 90 days old with no later sign of abandonment. A `closed` or `merged` linked PR, or an old claim comment with no follow-through, is an abandoned attempt and does not fail this check. In live mode on the Path Review repo, apply the scope.md house rule instead: other students' claim comments never fail this check there. | required |
| AI-contribution policy allows this workflow | The repo's `CONTRIBUTING.md` / `AI_POLICY.md` / stated contribution-policy line (eval repo-facts line / live docs) | Fails only on an outright ban on AI-generated code or documentation. Disclosure, personal-understanding, testing, or human-review conditions pass (they are terms to follow, not a ban). Silence (no stated policy) passes. | required |
| Approachable label | The issue's labels list | Passes when the issue carries a "good first issue," "help wanted," or "easy" label (or a maintainer comment explicitly calls it beginner-friendly). | preferred |
| Small footprint | The change described in the issue body | Passes when the described fix is confined to one file, one function, or one docs page, rather than spanning multiple files/modules. | preferred |

## Verdict rule

Accept if and only if every `required` check grades `pass`. A single `required` check graded `fail` rejects the issue, regardless of the others. `unclear` on a required check counts as `fail`: a first issue whose liveness, scope, claim status, or AI policy cannot actually be verified from the evidence is not one to take. `preferred` checks never change the verdict; report their grades, and use them only to rank issues that are already accepted (alongside the fit profile in `scope.md`).
